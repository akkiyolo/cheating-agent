## 2. Proposed architecture

```
mock-assessment/ (React, :3000)  ──/api──►  backend/ FastAPI (:8000)  ◄──/api── frontend/ dashboard (:5173)
        ▲  telemetry beacons                 │  assessment API, auth, code judge,
        │                                    │  agent control, security, evaluation
        │ Playwright (Chromium/Firefox/WebKit)│
   Agent runtime (LangGraph, thread per run) ─┘── Postgres (:5433, docker) · Redis (:6380, docker)
        │                                          Docker sandbox containers (network none)
        └── Claude (anthropic SDK, structured outputs, vision)
```

* **One backend process** hosts the mock assessment API, the code judge, the agent control plane, the
  security benchmark and evaluation APIs. Agent runs execute in a dedicated thread with their own
  event loop (Playwright needs subprocess support on Windows; isolates runs from request handling).
* **Agent** = LangGraph `StateGraph` over a typed Pydantic `AssessmentState`. Non-serialisable
  runtime objects (browser, LLM client, tool router) live in an `AgentRuntime` context, not in state.
* **Perception** = DOM snapshot via injected JS → `ObservationReducer` → compact semantic page model;
  accessibility snapshot via Playwright ARIA snapshot; vision via element/page screenshots.
* **Deterministic first**: page/question classification by heuristics, arithmetic by the calculator,
  code verified by sandbox execution. The LLM is used for reasoning that cannot be done otherwise.
* **Security benchmark** consumes *real* telemetry emitted by the mock assessment while the agent
  runs, plus *synthetic* telemetry (vision/audio/human baselines) generated by scenario generators.

## 4. Testing strategy

* **Unit** (pytest, no network): policy, resolver, reducer, classifiers, calculator, planner,
  time manager, loop detector, recovery, tool router, verifier, state, risk engine. LLM replaced by a
  scripted fake client implementing the same interface.
* **Integration**: FastAPI via `httpx.ASGITransport` on SQLite and on Postgres; sandbox against
  real Docker; browser adapter against the live mock assessment in all three engines.
* **E2E**: `scripts/e2e.py` launches backend + mock assessment, runs the real agent against a freshly
  randomised session in each browser with injected faults, verifies submission and results, writes
  trace + evaluation JSON. Requires an Anthropic API key for MCQ/text/image reasoning.
* **Frontend**: Vitest + React Testing Library for both React apps.

## 5. Security boundaries

* `TargetPolicy` (immutable, built from env at start-up, not reachable by the LLM): scheme, host,
  port, origin and path validation; extra hosts must resolve to loopback/private ranges.
* The agent only has the registered tools; unknown tool names and schema-invalid args are rejected.
  No shell, filesystem, network or policy-mutation tools exist.
* Generated code runs only in Docker: `--network none`, CPU/memory/PID limits, read-only rootfs,
  tmpfs, all capabilities dropped, non-root user, wall-clock timeout, `--rm`.
* CAPTCHA / MFA / identity verification / anti-automation challenges → `HUMAN_INTERVENTION_REQUIRED`
  with URL, screenshot, state, reason, timestamp. No circumvention code exists.
* The agent does not attempt to mask automation signals; the benchmark measures them.

## 6. Evaluation methodology

* **Agent**: accuracy is graded server-side against generated answer keys the agent never sees;
  every session draws a fresh random question set with randomised parameters and option order.
* **Browser matrix**: identical seeded assessments across Chromium/Firefox/WebKit.
* **Security**: positives = real agent-run telemetry + scenario injections; negatives = synthetic
  human-like baselines (documented as synthetic). Detection rate, FPR, FNR, latency, evidence quality.
* **Failure injection**: each fault class toggled per run; recovery success measured from traces.
* **Performance/load**: percentile latencies from traces; concurrent synthetic sessions measured
  with psutil and DB pool stats.
